7. Required API-preserving migration strategy
⯀js_CNTRL js_MODEL notes js_notes js_details js_VIEW ▶◀ ⬜ ↷  
This is the key point.
When moving from the current code to the clean architecture,
preserve the public behavior, not the exact function names, while
keeping the same semantics.
Recommended migration template:
- js_details.js
  - keep only bootstrapping and compatibility
  - call js_VIEW.init()
  - call js_MODEL.load()
  - pass DOM refs to js_VIEW
- js_VIEW.js
  - each click becomes a controller intent
  - no model calls directly
  - no direct array mutation
- js_CNTRL.js
  - owns the transition table
  - calls js_MODEL
  - handles state change events
- js_MODEL.js
  - delegates to notes.js
  - no DOM, no render logic
- notes.js
  - becomes the pure note-domain model
  - no UI logic
  - preserves deleted queue functions
- js_notes.js
  - becomes render helper only
  - no state machine logic
  - no deleted-note queue logic
8. Final recommendation
semantics state ownership adapter API ▶◀ ⬜ ↷  
The safest refactor is not “copy/paste split by file with partial removal.”
It is:

 - keep current semantics
 - identify all state-bearing functions
 - transfer ownership explicitly
 - preserve all deleted-note cleanup functions
 - keep js_details.js as adapter until the transition is complete
 - do not delete API surface before the controller/view split is complete

This is exactly the kind of migration that can be done
in a disciplined GVim workflow without losing traceability.
The critical mapping to keep from breaking the app:

 - editing state → js_CNTRL.js
 - data state → notes.js
 - DOM rendering → js_notes.js + js_VIEW.js
 - bootstrap glue → js_details.js
 - deleted-note queue cleanup → notes.js

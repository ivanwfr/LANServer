## The rendering pipeline (simplified)  ▶◀ ⬜ ✓ ↷ 

Each frame the browser runs through these stages:


 
  

   Operation
   
   process
  

 
 
  

   1. **JavaScript execution**
   
   your code runs, including rAF callbacks
  

  

   2. **Style calculation**
   
   the browser determines the final
computed style of every element
(CSS, inline styles, class changes, etc.)		
  

  

   3. **Layout**
   
   dimensions and positions are calculated based on computed styles
  

  

   4. **Paint**
   
   pixels are filled in for every visible element
  

  

   5. **Composite**
   
   visible layers are combined and sent to the display
  

 


At 60 Hz, you have roughly **16.7 ms** per frame for all of
this. At 120 Hz it's ~8.3 ms.
 




## Where `requestAnimationFrame` fits  ▶◀ ⬜ ✓ ↷ 

 `requestAnimationFrame` schedules a callback to run **after
 pending JavaScript tasks but before style calculation and layout**
 https://stackoverflow.com/questions/58027598/does-requestanimationframe-interfere-css-transitions.

 This is the key timing insight:
 - Your rAF callback is the **last point** your JavaScript can
 touch the DOM before the browser starts computing the next
 frame https://stackoverflow.com/questions/58027598/does-requestanimationframe-interfere-css-transitions

 - The browser **batches** all DOM/style changes made during
 your rAF callback and processes them together during the
 style/layout phase
 - This is fundamentally different from `setTimeout(fn, 16)`
 or `setInterval`, which fire at arbitrary times that may land
 mid-frame, causing wasted renders, screen tearing, or double-layouts
 https://www.grizzlypeaksoftware.com/library/css-animation-techniques-with-javascript-triggers-s5kflz0m

## The practical implication for style changes  ▶◀ ⬜ ✓ ↷ 


 When you change an element's style inside an rAF callback:
 
 

```js
 function animate(time) {
     const delta = time - lastTime;
     lastTime = time;
     
     element.style.transform = `translateX(${position}px)`;
... more style changes ...
     
     requestAnimationFrame(animate);
 }
 ```




 Here's what happens in sequence:
 
 1. rAF fires → your callback runs → you mutate `element.style`
 
 2. Browser finishes all rAF callbacks → moves to **Style**
    phase → recalculates computed styles for affected elements
 
 3. **Layout** phase → reflows if necessary
 
 4. **Paint** → fills pixels
 
 5. **Composite** → sends to screen
 
 If you change styles *outside* of rAF
 (e.g., in a click handler or `setTimeout`)
 you're at the mercy of when the browser decides
 to run the next paint.
 
 It might batch your change with the
 next frame's pipeline, or it might paint immediately
 — you don't control that cadence.

 




## rAF's real advantage: alignment, not speed  ▶◀ ⬜ ✓ ↷ 

rAF doesn't make the browser faster.
In fact, CSS transitions and rAF-based JS animations
perform nearly identically when both run on the main UI thread (*1)

 The advantage is **predictability**:
 
 - **Batching**:
    All DOM changes within one rAF callback are
    batched into a single style recalculation, avoiding layout
    thrashing (*2)
 
 - **Refresh-rate sync**:
   rAF runs at the display's native refresh
   rate, so at 120 Hz you get 120 updates per second, at 60 Hz you get 60 (*3)
 
 - **Background tab throttling**:
  rAF automatically pauses when
  the tab is hidden, saving CPU and battery (*4)
 
 - **Time-based animation**: The `timestamp` parameter lets
    you animate using elapsed time (delta-time), so motion stays
    smooth even if frames are dropped (*5)

## A common pitfall: layout thrashing  ▶◀ ⬜ ✓ ↷ 

 If you read and write styles in a tight loop, the browser is
 forced to flush layout synchronously between each read/write:

 

```js
   // BAD — triggers forced synchronous layout
   for (let i = 0; i < items.length; i++) {
   items[i].style.width = items[i].offsetWidth + 10 + 'px';
 
   // write
   const width = items[i].offsetWidth;  // read — forces layout
   flush
 }
 ```



 rAF doesn't prevent this — you just need to **read first, then
 write**, or batch reads and writes separately.
 




## Bottom line  ▶◀ ⬜ ✓ ↷ 


 `requestAnimationFrame` gives you **a window into the rendering
 pipeline**, not control over it.
 
 You get to say "I'm done modifying the DOM
 — now paint" and the browser does the rest.
 
 The control is temporal:
 your changes happen at the last possible optimal
 moment before the browser begins computing the next frame.
 
 You don't get hooks into layout, paint,
 or composite stages
 — those are opaque to JavaScript.
 
 For anything that can be expressed as a CSS transition or keyframe,
 prefer CSS since it can run off the main thread.
 
 Reach for rAF when you need per-frame JavaScript logic.

## The Airport: Browser Rendering Pipeline  ▶◀ ⬜ ✓ ↷ 


 **The DOM is the cargo manifest**
 
 Each element on your page is a crate on a pallet,
 tagged with its dimensions, weight, and
 destination gate (its position in the layout tree).
 
 Some crates are simple (a single `<p>` tag), others are nested inside other
 crates (child elements), and some are marked "fragile" or "heavy"
 (complex components, images, iframes).

 




**The fleet of planes is your JavaScript and network activity**  ▶◀ ⬜ ✓ ↷ 


 Each plane delivers new or updated crates to the airport.
 
 A `fetch()` response landing? That's a cargo plane touching down with a fresh
 pallet of DOM nodes.
 
 A `classList.add('active')` call? That's a forklift driver
 slapping a new label on an existing crate at its gate.
 
 A `style.transform = 'translateX(10px)'` change?
 That's a crate being physically moved to a different spot on
 the apron.

 




**The ground crew is the browser's rendering pipeline**  ▶◀ ⬜ ✓ ↷ 


 They work in shifts, and each shift has a strict deadline before
 the next one starts.
 Their job is to take all the crates currently sitting at gates
 and assemble them into a final, visible display
 — the painted frame that gets shown to the passenger (the user).

 




### The ground crew's workflow per shift  ▶◀ ⬜ ✓ ↷ 

Each shift (frame) follows a rigid sequence:


1. **Manifest review (Style recalculation)**  ▶◀ ⬜ ✓ ↷ 


 — The crew walks every gate and checks: "What does this crate actually look
 like right now?" A crate might have been re-tagged multiple
 times since the last shift (CSS cascade, inline styles, class
 changes). They reconcile everything into one final spec sheet
 per crate.

 




2. **Gate arrangement (Layout / Reflow)**  ▶◀ ⬜ ✓ ↷ 


 — Now they figure out where each crate physically sits on the tarmac.

 If crate A got bigger, crate B might need to slide over.
 Nested crates must fit inside their parent crates.

 This is the most expensive step
 — moving one heavy crate can force rearranging dozens of others.

 




3. **Wrapping and labeling (Paint)**  ▶◀ ⬜ ✓ ↷ 


 — The crates get wrapped in their final visual appearance:
 colors, borders, shadows, text glyphs, background images.
 
 Nothing moves anymore; this is purely cosmetic.

 




4. **Loading onto the departure shuttle (Composite)**  ▶◀ ⬜ ✓ ↷ 


 — All finished, wrapped crates are loaded onto a shuttle bus that
   drives them to the terminal window where passengers watch.
 
 This is the actual pixels hitting the screen.

 



 




### Where `requestAnimationFrame` fits  ▶◀ ⬜ ✓ ↷ 


Now here's the key part.  ▶◀ ⬜ ✓ ↷ 


 The ground crew works on a **fixed shift schedule**.
 At 60 Hz displays, a new shift starts every ~16.7 milliseconds.
 
 Between shifts, the crew is resting, and the tarmac is frozen.


 You're a warehouse manager who wants to move crates around.
 You could run out onto the tarmac at any random moment — shouting
 instructions while the crew is mid-shift.


 Sometimes you'll
 arrive just as they're finishing up, and your changes get included.


 Other times you'll arrive mid-arrangement, forcing them to
 stop what they're doing, re-check the manifest, redo the gate
 arrangement, and start wrapping again.


 This causes **jank** — the crew looks frantic, the shuttle leaves late,
 and passengers see stuttering.


 That's what happens when you mutate the DOM in a `setTimeout`
 or a click handler without thinking about timing.

 




**`requestAnimationFrame` is a radio channel to the shift supervisor**  ▶◀ ⬜ ✓ ↷ 

Instead of running onto the tarmac whenever you feel like it,
You pick up the radio and say:

   I have crate movements to announce,
   call me when the next shift is about to start


 The supervisor calls you back at exactly the right moment:
 — after the previous shift's shuttle has left,
 — but before the new shift's crew begins manifest review.

You shout all your changes at once:

 *"Move crate 42 three meters left! Retag crate 17 red!
 Stack crate 8 inside crate 3!"*

Then the supervisor says: *"Copy all. Crew, go."* 

 And the crew starts their shift
 with a clean, complete set of instructions.
 - No interruptions.
 - No rework.
 - One batch.

 



 




### What the radio *doesn't* give you  ▶◀ ⬜ ✓ ↷ 


 This is the crucial limitation.
 The radio lets you **talk to the crew before they start**,
 but it doesn't let you:



 - **Watch the crew work**  ▶◀ ⬜ ✓ ↷ 


 Once they hang up and start their shift, you're blind.
 
 You can't observe how long layout takes,
 whether paint is slow, or whether composite is bottlenecked.

 




 - **Tell them how to work**  ▶◀ ⬜ ✓ ↷ 


 You can say "move crate 42,"
 but not "use the hydraulic lift instead of dragging it."
 
 You can't control whether the browser uses
 the GPU compositor thread
 or forces a main-thread repaint.

 




 - **Skip a shift**  ▶◀ ⬜ ✓ ↷ 


 You can cancel your radio request (`cancelAnimationFrame`),
 but you can't pause the crew's shift schedule.

 




 - **Extend the shift**  ▶◀ ⬜ ✓ ↷ 


 If your crate-moving instructions are
 so complex that the crew runs out of time before the shuttle
 departs, the shuttle leaves empty.
 
 That's a dropped frame.
 
 The crew will catch up next shift, but the passenger saw a hitch.

 



 




### When CSS transitions skip the ground crew entirely  ▶◀ ⬜ ✓ ↷ 

 Here's where the metaphor extends beautifully.

 For certain crate types
 — specifically ones tagged `transform` or `opacity` —
 the airport has a **separate night crew**
 that works directly on the shuttle bus itself.


 These crates never go through manifest review,
 gate arrangement,
 or wrapping during regular shifts.


 The night crew just slides them around on the already-loaded shuttle,
 adjusting transparency with a dimmer switch.
 
 That's the **compositor thread**.
 CSS transitions on `transform` and `opacity`
 bypass the entire ground crew.
 
 The main crew never even knows those crates moved.
 
 This is why animating `left`, `width`, or `margin`
 (which require full manifest review + gate rearrangement every shift)
 is dramatically slower than animating `transform` and `opacity`.
